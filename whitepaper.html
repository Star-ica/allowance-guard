1. Abstract

RevokeX is a decentralized ERC-20 approval security dashboard built on BOT Chain. It enables users to discover, audit, and revoke token spending approvals granted to third-party contracts — a critical security hygiene step that most wallets and block explorers make difficult. RevokeX provides an on-chain audit trail, a risk-classified spender database, batch revocation, and a user-friendly security dashboard built entirely in Vanilla JavaScript with Solidity backend contracts and no traditional server infrastructure.

2. The Approval Vulnerability Problem

2.1 The ERC-20 Approve Pattern

The ERC-20 standard includes an approve(spender, amount) function that permits a third-party contract to transfer tokens on the owner's behalf. This mechanism underlies every DeFi protocol — DEXes, lending markets, staking platforms, and yield optimizers all require token approvals before they can move funds.

2.2 Why Approvals Are Dangerous

Several vulnerabilities arise from this design:

  • Unlimited approvals: To save gas and avoid re-approval UX friction, most DeFi frontends request type(uint256).max (infinite) approvals. If the approved contract is ever compromised, all tokens are at risk indefinitely.
  • Forgotten approvals: Users accumulate approvals across dozens of protocols over time. Even after a protocol is abandoned or deprecated, the approval persists on-chain.
  • Phishing approvals: Malicious sites trick users into approving a hacker-controlled address with unlimited spending rights, then drain wallets immediately or at a chosen moment.
  • Exploited contracts: Legitimate protocols can be hacked. Any wallet that holds an outstanding unlimited approval to a hacked contract loses all approved tokens.
  • No native discovery: MetaMask, standard wallets, and most explorers offer no view of outstanding approvals. Users cannot see their exposure without specialized tools.

2.3 Scope of the Problem

Studies of EVM chains show the average active DeFi wallet holds 8–15 outstanding ERC-20 approvals. A significant fraction are unlimited. This represents a persistent, compounding security debt that grows with each protocol interaction and never self-heals without deliberate revocation.

3. RevokeX Solution

3.1 Core Capabilities

  • Live Scanner: Read allowance(owner, spender) from ERC-20 tokens across a watchlist of token contracts and known spender addresses.
  • Risk Classification: Each spender is classified Unknown / Low / Medium / High / Critical based on admin-verified metadata and community flags.
  • One-Click Revoke: Execute approve(spender, 0) directly from the dashboard for any active approval.
  • Batch Revoke: Revoke up to 20 approvals in a single transaction via batchRevokeAllowances.
  • On-Chain Audit Log: Approvals and revocations are logged to the AllowanceRegistry contract, creating an immutable history queryable by any wallet.
  • Token Watchlist: Users maintain a personal on-chain list of tokens to monitor, persisted via the TokenWatchlist contract.

3.2 Design Principles

  • Non-custodial: RevokeX never holds tokens. All approvals and revocations execute directly on the token contract.
  • No backend: Pure on-chain + ethers.js frontend. No server, no database, no API keys required.
  • Transparent: All contract code is open source and verifiable on the BOT Chain explorer.
  • Ergonomic: Single-page application with security dashboard, batch operations, and risk indicators designed for non-technical users.

7. Security Design

7.1 Non-Custodial Revocation

RevokeX's revokeAllowance function calls IERC20(token).approve(spender, 0) where msg.sender is the wallet owner — not the contract. The contract never holds tokens or approvals itself. It is a stateless relay that only emits audit events and delegates the actual approval change to the token contract directly.

7.2 Batch Safety

The batchRevokeAllowances function uses try/catch per token so a failure on one token (e.g., a non-standard token that reverts on approve) does not block the entire batch. Failed revocations are skipped silently; successful ones emit events. The batch is capped at 20 items to prevent gas limit issues.

7.3 Reentrancy Protection

All state-changing external calls use ReentrancyGuard from OpenZeppelin. The CEI (Checks-Effects-Interactions) pattern is followed: internal state is updated before external ERC-20 calls.

7.4 Pause Mechanism

The owner can pause the registry to halt new log and revoke operations in an emergency. This protects users from interacting with a compromised frontend while a fix is deployed.

7.5 Limitations

  • RevokeX can only discover approvals for tokens the user explicitly adds to their scan list. It does not automatically enumerate all ERC-20 tokens.
  • The audit log only covers approvals recorded via the RevokeX UI. Historical approvals made through other frontends are not in the registry unless manually logged.
  • Some non-standard ERC-20 tokens may revert on approve(spender, 0). The batch revoke skips these; single revoke returns an error.

  (unlimited_approvals × 20) +
  (high_or_critical × 15) +

Score 0–15: Low risk (green). 16–40: Moderate (yellow). 41–70: High (orange). 71–100: Critical (red).

8.3 DEMO Mode

When DEMO = true (default before deployment), the application uses hardcoded sample approvals and simulates revocations client-side. No wallet or deployed contract is required. Set DEMO = false and update CONFIG.contracts after deployment.

10. Disclaimer

RevokeX is provided as-is for educational and security hygiene purposes. It does not constitute financial or investment advice. Users are solely responsible for their own token approvals and revocations. Smart contracts have been developed with security best practices but have not been professionally audited. Use at your own risk. Always verify contract addresses and transaction details before signing.

Revoking an approval will prevent the approved protocol from accessing your tokens — this may disrupt active positions (open orders, staked assets, liquidity positions) in those protocols. Review implications before revoking.
